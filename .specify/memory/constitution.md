## Core Principles

### I. Code Generation as Framework Infrastructure

Code generation tools are treated as **framework infrastructure**, not applications. This means:

- **Reusable Components**: All generators share common utilities for AST manipulation, type analysis, package loading, and file operations.
- **Extensibility by Design**: New generators MUST be implementable without modifying core infrastructure; the framework provides interfaces and patterns that generators implement.
- **Export for Reuse**: Packages under this module are exported for possible reuse, though stability is not guaranteed.
- **Shared Patterns**: Common patterns for handling generics, embedded types, complex type relationships, directive comments, and import management MUST be extracted as reusable utilities.

**Rationale**: The project explicitly states it is a "swiss army knife" framework. Treating it as infrastructure ensures consistency across generators and reduces duplication.

### II. Type Safety and AST-Based Generation

Code generation MUST maintain Go's type safety guarantees and leverage full type information:

- **Full Type Loading**: MUST use `golang.org/x/tools/go/packages` with complete type information, not just syntax parsing.
- **Type Graph Analysis**: Complex type dependencies MUST be modeled as graphs (Parent/Children edges) to handle cross-package relationships correctly.
- **AST Manipulation Required**: Generated code MUST be produced via AST manipulation (`github.com/dave/dst`) to preserve formatting and comments, not string concatenation.
- **Generic-Aware**: Generators MUST handle Go generics correctly, distinguishing between generic and non-generic type instantiations.

**Rationale**: String-based generation is fragile and cannot reason about types. AST-based generation with full type information ensures correctness and maintainability.

### III. Directive-Driven Customization

Per-symbol customization MUST be available through directive comments, with global defaults configurable:

- **Comment Syntax**: Directives use the format `//generatorname:directivename` (e.g., `//cloner:copyptr`).
- **Per-Field Override**: Field-level directives MUST override global configuration for that specific field.
- **Clear Precedence**: Local (field-level) > Global (config-level) precedence MUST be documented and enforced.
- **Fail-Fast on Invalid Directives**: Unknown or malformed directives MUST cause generation to fail with clear error messages.

**Rationale**: One-size-fits-all generation is insufficient for real-world use cases. Directive comments provide fine-grained control while keeping the Go source as the single source of truth.

### IV. Generated Code Discipline

All generated code MUST follow strict conventions and quality standards:

- **DO NOT EDIT Header**: Every generated file MUST start with `// Code generated by github.com/ngicks/go-codegen/codegen DO NOT EDIT.`
- **Consistent Suffixes**: Generated files MUST use predictable suffixes (`.clone.go`, `.und_patch.go`, `.und_plain.go`, `.und_validator.go`).
- **Auto-Formatting**: Generated code MUST be processed with `goimports` before writing to ensure correct imports and formatting.
- **Idiomatic Go**: Generated code MUST follow Go conventions (naming, error handling, receiver patterns).
- **No Manual Edits**: Generated files MUST never be manually edited; all customization goes through directives or config.

**Rationale**: Generated code is a build artifact. Consistency and automation prevent maintenance burden and confusion.

### V. Security Constraints for Path Handling

Code generation involves file system operations that MUST be strictly controlled:

- **Relative Paths Only**: Package paths MUST be relative to the working directory, never absolute.
- **No Path Traversal**: Validation MUST reject paths containing `..` or attempting to escape the working directory.
- **Working Directory Root**: All output files MUST be written within the working directory tree.
- **Clear Error Messages**: Path validation failures MUST produce actionable error messages indicating the constraint violated.

**Rationale**: Code generators run with developer privileges. Path traversal vulnerabilities could allow arbitrary file overwrites.

### VI. Testing with Generated Artifacts (NON-NEGOTIABLE)

Tests MUST verify actual generated code, not mocked behavior:

- **Real Generation**: Test suite MUST invoke actual code generation and compile the results.
- **Integration Tests**: `internal/generationtests` and `internal/tests` directories provide patterns for testing generators end-to-end.
- **Compilation as Test**: Generated code MUST compile successfully; compilation failures are test failures.
- **goimports Required**: Tests depend on `goimports` being installed (`golang.org/x/tools/cmd/goimports@latest`).
- **Before Implementation**: For new generators or features, write tests that generate expected code first, verify they fail, then implement.

**Rationale**: Unit testing code generators without verifying actual output is insufficient. The proof is in successfully compiling and using the generated code.

### VII. Matcher System for Selective Generation

Type matching (deciding what needs generation) MUST be configurable and composable:

- **MatcherConfig**: Configuration controls rules for channels, functions, interfaces, no-copy types, and other special cases.
- **Graph-Aware Matching**: Matchers operate on the type graph, not individual types in isolation, to handle dependencies.
- **Explicit Inclusion/Exclusion**: Users MUST be able to explicitly include or exclude types via configuration or directives.
- **Default to Safe**: When unsure, default to NOT generating code; users can explicitly opt-in.

**Rationale**: Generating code for every type is wasteful and often incorrect (e.g., copying uncopyable types). Configurable matching provides control.

## Quality Gates

Before merging any code, the following gates MUST pass:

1. **Compilation**: All generated test code MUST compile without errors.
2. **Test Passing**: `go test ./...` MUST pass.
3. **Generation Up-to-Date**: `go generate ./...` MUST be run and any changes committed before tests.
4. **No Manual Edits**: Generated files MUST show the standard header and match what generators produce.

## Development Workflow

### Adding New Generators

1. **Design Phase**:
   - Define generator purpose and scope
   - Identify reusable components vs. generator-specific logic
   - Design directive syntax and configuration schema
   - Document example inputs and expected outputs

2. **Implementation Phase**:
   - Implement matcher logic (what types to generate for)
   - Implement AST generation logic
   - Add directive comment parsing
   - Integrate with `suffixwriter.Writer` for file output

3. **Testing Phase**:
   - Create test package in `internal/generationtests` or `internal/tests`
   - Write test inputs (Go source files with types)
   - Write expected output verification
   - Verify compilation and execution of generated code

4. **Documentation Phase**:
   - Update README with new generator capabilities
   - Document directives and configuration options
   - Provide usage examples

### Modifying Existing Generators

1. **Behavior Change**:
   - Update or add tests showing new behavior
   - Verify tests fail before implementation (Red)
   - Implement change (Green)
   - Refactor if needed
   - Update documentation

2. **Directive Addition**:
   - Add test cases with new directive
   - Implement parsing and handling
   - Document directive usage

## Governance

### Constitution Authority

This constitution defines the non-negotiable principles for go-codegen development. All design decisions, code reviews, and feature additions MUST comply with these principles.

### Amendment Process

1. **Proposal**: Document proposed amendment with rationale and impact analysis.
2. **Review**: Assess compatibility with existing generators and tests.
3. **Migration Plan**: If breaking, define migration path for existing generators.
4. **Version Bump**:
   - **MAJOR**: Backward-incompatible principle changes (e.g., removing AST requirement)
   - **MINOR**: New principles or material guidance expansion (e.g., adding observability principle)
   - **PATCH**: Clarifications, wording improvements, non-semantic fixes
5. **Template Sync**: Update all `.specify/templates/*.md` files to reflect changes.
6. **Documentation**: Update constitution version, amendment date, and impact report.

### Compliance Review

- **Pull Requests**: All PRs MUST reference applicable principles when adding features or generators.
- **Architecture Decisions**: Major architectural changes MUST be justified against principles or propose amendments.
- **Principle Conflicts**: When implementation conflicts with principles, principle takes precedence unless amended.

### Runtime Development Guidance

For day-to-day development guidance, coding patterns, and best practices, refer to:
- **CLAUDE.md**: Instructions for Claude Code when working with this repository
- **Serena Memories**: Project-specific information stored in Serena MCP tool
- **README.md**: Getting started, dependencies, and usage examples

These documents provide **implementation guidance** but do NOT override constitutional principles.
